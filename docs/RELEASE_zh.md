# 通过标签自动发布

先让分支 CI 测试通过，再给该 commit 打一个未使用的版本标签并推送即可。
不需要修改源码版本号、额外创建 commit，也不需要手动点击创建 Release。
例如：

```sh
git tag v0.1.2 <已经通过测试的commit>
git push origin v0.1.2
```

该 commit 必须已经包含本工作流。旧标签仍使用旧代码中的工作流；本改动不会
自动修复或重新发布历史版本。不要移动或强推已经公开的标签。

## 构建和版本

标签是发布版本的唯一来源，支持 `vX.Y.Z` 和 `vX.Y.Z-rc.1` 等预发布标签。
数字段不允许多余前导零，不支持 `+...` 构建后缀。构建时通过 Go 链接参数注入，
元数据和真实插件使用同一版本；不再手改 buildinfo。

完整标签保存为 `build_tag`。为保持原有部署文件名校验，`v1.2.3-rc.1` 对应
插件版本 `1.2.3`、文件名 `opencode-v1.2.3.so`，外层压缩包保留完整标签，
GitHub 自动标记为预发布。本地默认和分支/PR 构建为 `0.0.0`、`build_tag=dev`，
不作为正式发布。

分支 push 和 PR 只运行 CI。标签 push 运行 Linux amd64、arm64 原生构建，保留
全部离线测试、vet、race、Python/shell 测试和原生宿主门禁。宿主实际加载插件，
核对注册版本与元数据；CI 另核对构建版本、完整标签、干净源码 commit、ELF 架构、
导出符号和校验和。只有双架构全部成功才进入发布。

## 草稿上传与失败重试

打包验证全部本地资产后才创建草稿，依次上传双架构压缩包和校验文件并核对远端
摘要，最后上传完成清单；全部资产验证完成后才公开发布。不再监听 release
发布事件，因此没有重复触发链路。只有发布 job 有 contents: write 权限。

构建或打包失败不会创建 Release；上传失败保留草稿，可重跑失败 job。相同资产
直接保留，缺失资产补传，仅允许清理零字节失败上传占位记录。不同内容的同名资产
会报错，绝不覆盖。已经公开且完全匹配的版本只核验；已有不完整或不同的公开版本
不会被修改。发布请求响应丢失时应读回核验，不能认为一定失败。

支持不可变 Release，因为上传发生在草稿阶段，不会关闭不可变保护。重跑构建若
因工具链或 runner 变化造成二进制不同，应使用新标签，不能覆盖历史资产。

## 安装

每个版本提供 amd64、arm64 压缩包、外部 SHA256SUMS 和 release.json 完成清单。
下载对应架构，先核对压缩包 SHA-256，再解压并核对内部 SHA256SUMS。保留原 `.so`
文件名，CPA 插件目录只留一个目标版本。原生 glibc 构建不代表适用所有 Linux；
请核对归档中的 glibc 要求。校验和不是独立签名。

本地发布测试使用模拟 GitHub API 和合成 ELF，不能代替真实 arm64 原生门禁或
线上发布权限验证。详细英文说明见 [RELEASE.md](RELEASE.md)。已知宿主 disable
回归仍可单独运行 `make hostcheck-known-bug`，不计入通过的标准门禁。
